## 本轮新增改动（2026-03-28）

### 1. qB 会话管理进一步收口

- 不再只在“加种接口返回 `403`”时才尝试恢复
- 改为把“查询当前下载数”“添加种子文件”等 qB API 请求统一走同一套会话处理逻辑
- 如果本地 qB Cookie Jar 不存在，会先自动重新登录
- 所有 qB API 请求现在都会同时：
  - 发送已有 Cookie
  - 回写最新 Cookie 到 Cookie Jar

### 2. 加入主动刷新 qB 会话

- 新增配置项：`qb.session_refresh_seconds`
- 默认值：`1500`
- 含义：qB 会话年龄达到这个秒数后，下一次 qB API 请求前会主动重登
- 设为 `0` 时表示禁用主动刷新

### 3. qB `403` 的日志可观测性增强

- 如果任一 qB API 请求返回 `403`
  - 会先记录本次请求标签、HTTP 状态和返回内容
  - 再记录当前会话年龄
  - 然后自动重新登录并重试一次
- 重试后的最终 HTTP 状态和返回内容也会被单独记录
- 这样后续可以区分：
  - 是首次请求就成功
  - 还是 `403` 后自动恢复成功
  - 或者重登后仍失败

## 本轮已完成的改动

### 1. 聊天区解析逻辑重构

- 不再依赖旧版脚本中的乱码 `grep` 正则
- 改为使用 Python 解析聊天区 HTML
- 读取方式改为原始字节，再按以下编码依次尝试解码：
  - `utf-8`
  - `gb18030`
  - `big5`
  - `latin-1`
- 解析时会：
  - 识别“完成了一次上传X.XX下载0.00的魔法”
  - 优先提取真实种子链接 `details.php?id=...`
  - 排除 `userdetails.php?id=...` 之类的误命中
  - 去重后输出 `种子ID + 原始聊天文本`

### 2. 日志增强

- 增加日志：
  - `发现新增种子：种子ID=...`
  - `命中聊天文本：种子ID=...，文本=...`
  - `qB 添加种子文件：HTTP=...，返回内容=...`
- 便于区分：
  - 是否真的命中了聊天消息
  - 命中的是哪一条文本
  - 失败发生在 U2 侧、下载侧，还是 qB 侧

### 3. 首次运行逻辑保留

- 首次运行只初始化当前聊天区可见消息为“基线事件”
- 不会把历史命中的旧种子一次性推送到 qB

### 4. 日志轮转

- `install_systemd.sh` 已写入 `logrotate`
- 目的是避免日志过大导致查看、编辑或运行卡顿

### 5. qB 请求补强

- 对 qB Web API 请求增加了：
  - `Referer`
  - `Origin`
- 如果加种返回 `403 Forbidden`，脚本会自动：
  - 重新登录 qB
  - 再重试一次加种

## 当前待观察问题

### qB 返回 `403 Forbidden`

在 2026-03-24 11:31 至 11:38 的日志中，出现过多次：

- `qB 添加种子文件：HTTP=403，返回内容=Forbidden`

这类错误更像是：

- qB WebUI 会话失效
- qB 的 CSRF / Host / Origin / Referer 校验触发
- 反向代理或 qB WebUI 的访问策略限制

暂时不优先判断为“种子已存在”，因为：

- qB 官方 Web API 文档中，重复种子并不通常表现为 `403`
- `403` 更接近鉴权或请求来源被拒绝

本轮已经加入“自动重登 + 重试一次”的处理，后续需继续观察新日志。

补充：

- 现在不仅“加种”会自动恢复，其他 qB API 请求也会一起复用这套逻辑
- 另外新增了“会话达到一定年龄就主动刷新”的机制，用来降低 `403` 触发频率

## 下一步建议

### 若下一次仍出现 `403`

- 检查 VPS 上 qB WebUI 设置：
  - Host header 校验
  - CSRF 防护
  - 反向代理相关限制
- 检查 qB 是否只接受特定来源的 WebUI 请求
- 必要时增加更详细的 qB 调试日志
- 如果连“主动刷新后 + 重新登录重试后”仍然 `403`，问题就更像是：
  - qB WebUI 配置限制
  - 反向代理转发头不一致
  - WebUI 来源校验策略不接受当前请求

### 若下一次重试成功

- 说明主要问题是 qB 会话或来源校验
- 可以考虑进一步优化：
  - 把重试次数、错误类型记入日志
  - 按接口分别统计 `403` 出现频率
